# How the text-to-schema pipeline works

`run_pipeline.py` reads its input path, model settings, prompt paths, and output paths from the root `.env`. Run it with `python run_pipeline.py`. The configured input is UTF-8 JSONL, with one database specification per record. By default, the `question` field supplies the specification and `id` supplies the report ID. When the ID is missing, the ID uses the physical input line number, such as `line-3`. [Batch setup](README.md)

## From specification to SQL

The stages follow Figure 1 in the project proposal. [Project proposal](../formal_verification_guided_text2schema.pdf)

1. The extraction prompt asks the model for one JSON object with `attribute_types` and `functional_dependencies`. `attribute_types` lists each attribute with its SQLite type. The pipeline derives the attribute list from those keys, including attributes absent from all functional dependencies (FDs). It validates the types and FD syntax before asking for a schema. The extraction runs once per specification. [Extraction prompt](prompts/extract_fds_attributes_and_types_prompt.txt)
2. The schema prompt asks the model to construct relations over the extracted attributes using the FDs. The user message carries the original specification, attribute names, and FDs. Revisions also receive the previous proposal and its latest feedback. The extracted names and FDs stay fixed across attempts. The response uses one relation declaration per line and `<u>` tags around every column of a declared primary key. [Schema prompt](prompts/generate_relational_schema_prompt.txt)
3. The pipeline parses the candidate and checks that it contains exactly the extracted attributes. The verifier then checks 2NF, 3NF, lossless decomposition, and dependency preservation under the extracted FDs. When a proposal is rejected, its feedback describes the reason for the next attempt. [Verifier guide](../verifier/README.md)
4. After verification passes, the SQL generator uses the extracted types and the proposed relations to produce SQLite `CREATE TABLE` statements. If a candidate passes verification and SQL generation, processing moves to the next record. The default `PIPELINE_MAX_ITERATIONS=3` includes the first proposal. When it reaches the limit without a passing schema, the record is marked `exhausted` and contains no SQL. [CREATE query generator guide](../create_query_generator/README.md)

Malformed input, invalid extraction, and model call failures are recorded against the affected record. The batch continues processing subsequent records. The formal checks apply to the extracted attributes and FDs.

## CSV reports

Both reports follow input order. Use `spec_id` and `input_line` together to identify the source record, including when IDs repeat. In either report, `prompt` is a JSON array containing the exact system and user messages passed to the model client. `model_response` holds the original assistant text, including formatting such as Markdown fences if present. Unavailable values leave empty cells.

### Batch results

`PIPELINE_OUTPUT_CSV` defaults to `pipeline/results.csv`. Each valid record has an `extraction` row with iteration `0`, followed by one `schema` row per proposal starting at iteration `1`. Malformed input records have stage `input` and a blank iteration. Statuses include `extracted`, `rejected`, `exhausted`, `verified`, and `error`. The `feedback` field gives the reason for a rejection or error. Only a verified row includes generated SQL. Token counts in this report apply to schema requests.

```text
spec_id,input_line,stage,iteration,status,database_specification,prompt,model_response,input_tokens,output_tokens,total_tokens,attributes,attribute_types,functional_dependencies,relational_schema,feedback,verification,create_queries
```

### Extraction results

`PIPELINE_EXTRACTION_CSV` defaults to `pipeline/extraction_results.csv` with the default batch results path. If the setting is omitted, the extraction CSV goes beside the batch results and adds `extraction_` before the results filename. It records one row for each extraction attempt, including failed attempts. Each row can contain the source specification, chat messages, assistant text, token counts, and the extracted `attributes`, `attribute_types`, and `functional_dependencies`. The `status` and `feedback` fields describe the extraction outcome.

```text
spec_id,input_line,status,database_specification,prompt,model_response,input_tokens,output_tokens,total_tokens,attributes,attribute_types,functional_dependencies,feedback
```

Read `prompt`, `attributes`, `attribute_types`, `functional_dependencies`, `verification`, and `create_queries` as JSON when populated. `input_tokens` counts tokens sent to the model, and `output_tokens` counts tokens generated by the model. The pipeline reads these counts from `prompt_tokens` and `completion_tokens` for hosted calls, and from `prompt_eval_count` and `eval_count` for native Ollama. Hosted calls use the original usage fields when LiteLLM exposes an OpenAI-format response. Other hosted calls use LiteLLM's normalized usage, which may supply zero for an omitted counter. When the available metadata omits a total but supplies both counts, the pipeline adds them. Missing counters remain blank when the backend exposes them as missing. [LiteLLM response format](https://docs.litellm.ai/docs/learn/python_sdk_quickstart) · [Ollama chat response](https://docs.ollama.com/api/chat)

The batch stages both reports in their destination directories and finishes serializing them before publishing either. It replaces the extraction report first and the batch results second, with each replacement atomic. Setup or serialization errors preserve the previous reports. If replacing the batch results fails, the batch rolls back the extraction replacement.

## Call from Python

```python
from pipeline.llm import LLMClient
from pipeline.run import run_pipeline

spec = "Each employee has a unique integer ID and a full name."
client = LLMClient("qwen3:8b", backend="ollama")
result = run_pipeline(spec, client, max_iterations=3)

if result["verified"]:
    print("\n\n".join(result["create_queries"]))
else:
    print(result["feedback"])
```

The result includes `verified`, `attribute_types`, `functional_dependencies`, `relational_schema`, `create_queries`, and `feedback`. Each entry in `attempts` records the iteration, proposed schema, feedback, and verification report. The report is `None` when parsing or attribute coverage rejects a proposal before the formal checks. Invalid extraction raises `ExtractionError` before schema generation starts.
