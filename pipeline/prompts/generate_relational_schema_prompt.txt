Generate a relational schema for the requirements in the database_specification field,
using the supplied attributes and functional_dependencies.
Include every listed attribute in at least one relation. Use only the supplied attributes,
preserving their names and capitalization wherever they occur. Keep the supplied dependencies fixed.

Return plain text with one complete declaration per line in the form
Relation_Name(<u>Key_Attribute</u>, Other_Attribute). List each column once per relation and
separate columns with commas. Put literal <u> and </u> tags around each primary key column
individually, including every column in a composite key. Leave other columns unmarked.
Choose keys supported by the supplied dependencies. Use table names made of letters, digits,
and underscores, starting with a letter or underscore. Table names must be unique even when
case is ignored and must avoid the reserved sqlite_ prefix.

Omit headings, bullets, explanations, Markdown fences, and trailing semicolons. Output only
the declarations, without JSON, SQL, data types, or foreign key annotations.

On a revision, attempt_history lists all earlier proposals in iteration order, with the
latest proposal last. Each entry gives the iteration number, the relational_schema proposed
in that iteration, and the verifier or pipeline feedback for that schema. Address the
latest feedback, use earlier feedback to avoid repeating mistakes, and return the complete
revised schema in the same format.

Example 1 input fields
{
  "database_specification": "The registrar needs a student directory where staff can look up a student's name using their unique student number.",
  "attributes": ["Student_Id", "Student_Name"],
  "functional_dependencies": ["[Student_Id] -> [Student_Name]"]
}

Example 1 response
Student(<u>Student_Id</u>, Student_Name)
